## ⚙️ Remediation Log — Pass 2 (Bug #1 recast ship-blocker) — 2026-06-06

> A **second, separate** fix pass, run after the JB2A pass above. It addresses **Bug #1 — recast over a live Tulpa destroys BOTH Tulpas and silently aborts** — the first of the two RED-causing ship-blockers. **This log is the authoritative current state for Bug #1.** At the time of this pass the build was **still RED** due to Bug #2; that was subsequently resolved in *Remediation Log — Pass 3* below.
>
> **Process honored (full superpowers `systematic-debugging` loop):** the exact cascade was **reproduced LIVE via Claude-in-Chrome** against this same world *before* any code change — both dragons gone, caster effects empty, slot consumed, the two errors — and the per-document delete order was captured with a `.delete()` monkeypatch on the `ActiveEffect`/`TokenDocument` prototypes. Root cause was then traced through dnd5e **and** midi-qol source, a fix was planned, **explained in plain English and explicitly approved by the requester** ("Approved explicitly"), and only then implemented — TDD-first for the one pure piece. No `_source/` field changed → no CLAUDE.md locked-field edit required.

### (1) What was fixed

The recast cleanup used to run in `onPostSummon` — **after** dnd5e had already created the new token — and it tore the old Tulpa down by deleting the **old token first**. That single ordering choice caused the whole cascade (call order captured live):

1. Outer `performDismissCleanup` deletes the **old token**.
2. That fires `onPreDeleteToken`, which deletes the **old anchor** with `{skipTokenTeardown:true}` but **no `skipFunnel`** → **re-enters** the dismissal funnel.
3. + 4. The re-entrant funnel *and* the outer cleanup each call `findSystemSummonAE` and both delete the system **"Summon: Manifest Tulpa"** AE — the second delete throws `ActiveEffect "<id>" does not exist!` (the UI banner).
5. Deleting that "Summon:" AE cascades to delete the **new token** (mechanism below).
6. Control returns to the old recast block, whose own `previous.delete({skipFunnel:true})` runs against the anchor step 2 already deleted → **uncaught** `undefined id … EmbeddedCollection` → the cast aborts before the dialog.

**Mechanism correction — why the *new* token dies (the crux the original §5 model got partly wrong).** The original report guessed `findSystemSummonAE` swept a *separate* new-summon AE. Live + source research shows it is subtler and worse:
- **dnd5e core never makes a token a dependent** — `ActiveEffect5e#_onDelete → getDependents()` returns only AEs/Items carrying `flags.dnd5e.dependentOn`, never tokens.
- **midi-qol extends dnd5e's dependent-document mixin onto the *Token* document class.** With this world's `autoRemoveSummonedCreature = TRUE`, midi pins every summoned token to a **"Summon: `<item.name>`" AE reused BY NAME** (`flags.dnd5e.dependentOn = <AE uuid>`). Across recasts the **old and new tokens get pinned to the *same* reused AE**, so deleting it during the old teardown cascades — via midi's token-dependent path — to the **new** token too.
- **Manifest Tulpa does not concentrate** (confirmed live: no "Concentrating:" AE), so concentration plays no part. DAE is a passive bystander (creates no summon AE, deletes no tokens).

**The three load-bearing choices, in plain English:**
- **Through the funnel (not direct cleanup):** `anchor.delete()` removes the anchor from the collection *before* the post-delete `deleteActiveEffect` hook runs the cleanup. So when cleanup later deletes the old token → `onPreDeleteToken` → `findPreviousAnchor` returns **null** → the funnel **does not re-enter**. That re-entrancy *was* the bug. (Foundry's order — `preDeleteDocument` before removal, the typed `deleteActiveEffect` hook after removal — is what makes this safe.)
- **In `preUseActivity` (not `postSummon`):** it fires after slot selection but *before* the placement crosshair, so the old token + anchor + "Summon:" AE are fully gone **before the new token exists**. midi-qol then gives the new token a **fresh** "Summon:" AE that nothing else is pinned to → no collateral kill.
- **`skipAnimation`:** without it the up-to-15 s dismiss animation runs *before* the summon-AE sweep; a fast placement could create the new token (and let midi pin it to the still-alive old AE) before the sweep lands. `skipAnimation` collapses the old teardown to fast DB ops that finish well before the crosshair is placed.

**Effect on smoke grades — read carefully:** Bug #1 is **fixed at the code level and unit-locked where feasible, but NOT yet live-verified.** R15 and R43 are deliberately **left at FAIL** in §4.2 — the fix is timing/hook-ordering and cannot be proven by unit test without a Foundry mock harness (none exists in `tests/`). At the time of this pass the build remained **RED** because Bug #2 (duration banner) was still open — that was subsequently fixed in *Remediation Log — Pass 3*; see R43's updated grade in §4.2.

**Known limitation (disclosed; not a blocker).** The recast pre-dismissal rides on `dnd5e.preUseActivity`, which fires on the **inline** cast path (click spell → crosshair → place). The **chat-card "Summon"-button** deferred-cast path may not fire `preUseActivity`, so a recast triggered *that* way would not pre-dismiss → it would leave **two live Tulpas** (no crash — graceful degradation), not the old double-destroy. The live/primary cast path is inline, so this is an unexercised edge, flagged for the next smoke.

**Tradeoff (consistent with invariant #2).** The slot is consumed before the dialog, and the previous Tulpa is now dismissed at slot-commit time. Cancelling at the placement crosshair therefore leaves **no** Tulpa and a spent slot — acceptable because recast means "replace," and the spent-on-cancel slot is the pre-existing invariant-#2 behavior.

### (1) What was fixed

The root cause (correcting the §5 Bug #2 diagnosis): **times-up expires both same-duration AEs in a single batch** — the dnd5e "Summon: Manifest Tulpa" AE and the module anchor "Manifest Tulpa (active)" AE both carry `duration.seconds = 3600`. The Summon AE owns the Tulpa token as a `getDependents()` dependent, so deleting it cascades to delete the token (s=2). That token-delete fires `onPreDeleteToken`, which deletes the anchor `V2ZGiEC0FzqbMTwH` with `dismissReason:"manual"` (s=3) — stamping the wrong reason (Bug #3). When times-up then tries to delete that same anchor (s=4), it is already gone → **`ActiveEffect "V2ZGiEC0FzqbMTwH" does not exist!`** red banner (Bug #2). The module's own guarded token delete (the `.has()` membership check at dismiss-flow.js L93) never fires on this path because `skipTokenTeardown:true` was set at s=3 — the banner is entirely times-up's second anchor delete, not the module.

**Critical correction:** the banner id `V2ZGiEC0FzqbMTwH` is the **ANCHOR AE id**, not a token id. The §5 Bug #2 section's token-double-delete narrative and the token-ownership-lock proposal are WRONG; live capture shows it is an anchor double-delete. The fix is in `onPreDeleteToken`, not in a per-`tulpaUuid` in-flight set.

A null/undefined/absent `remaining` is NOT expired (manual-delete path). Node-testable; reads only `anchor.duration.remaining` so it works on test fakes and live AE documents alike. |
| **B** | [`modules/dismiss-flow.js`](../../../modules/dismiss-flow.js) | **The fix.** In `onPreDeleteToken`, immediately after `if (!anchor) return;` and before the `anchor.delete({…dismissReason:"manual"…})`: `if (isAnchorDurationExpired(anchor)) return;`. On duration expiry the anchor's `remaining <= 0` → we DEFER; times-up's s=4 anchor delete becomes the SOLE anchor delete (fixes Bug #2 — no double-delete, no banner), and because it carries no module options, the funnel re-enters and `inferReason` resolves "duration" (fixes Bug #3). **The three load-bearing choices, in plain English:**
- **Defer to times-up (not suppress the second delete):** `onPreDeleteToken` simply returns without touching the anchor. times-up's own anchor delete (s=4) then runs on a still-present document and the funnel re-enters cleanly — no banner.
- **Discriminator is `duration.remaining <= 0` (not a per-`tulpaUuid` in-flight set):** the simpler and more surgical fix. The anchor's duration has already ticked to zero when times-up fires, so the remaining value is a reliable signal with no race risk.

### (1) What was fixed

- **Bug #4 — invalid `isDeath` DAE specialDuration (MINIMAL fix per requester).** The anchor AE carried `dae.specialDuration = ["zeroHP", "isDeath"]`; DAE 13.0.26 has no `isDeath` key (verified live via `DAE.daeSpecialDurations()`), so it was a silent no-op that *implied* a death trigger existed. Per the requester's explicit decision, the fix is **minimal**: drop the dead key and keep `zeroHP` (which already fires at HP ≤ 0, covering every realistic death). **No new death listener was added.** The literal moved to a named constant `ANCHOR_SPECIAL_DURATIONS = ["zeroHP"]` in [`modules/constants.js`](../../../modules/constants.js); [`modules/cast-flow.js`](../../../modules/cast-flow.js) `createAnchorAE` references it.
- **Bug #6 — orphan combatant left in the tracker after every dismissal.** Foundry does not remove a combatant when its token is deleted — it survives with `.token` resolving to `null` while `tokenId` still points at the deleted token. `performDismissCleanup` deleted the Tulpa token but never its combatant, leaving a ghost row in the tracker after **every** dismissal. Fixed with a new pure helper `collectTulpaCombatants(combats, tokenId)` in [`modules/dismiss-helpers.js`](../../../modules/dismiss-helpers.js), called from [`modules/dismiss-flow.js`](../../../modules/dismiss-flow.js) right after token teardown (tokenId read from the anchor's `tulpaTokenId` flag).
- **Bug #7 — system "Summon:" AE leaked on a cancelled or over-budget cast.** dnd5e/midi-qol creates the "Summon: Manifest Tulpa" AE on the caster async (~2–4 s after the activity use), independent of our flow. When the dialog is cancelled or the mods exceed budget, the cast aborts **before** the anchor exists, so the anchor-driven funnel never runs and the orphaned Summon AE stayed on the caster sheet. Fixed: `abortAndCleanup` in [`modules/cast-flow.js`](../../../modules/cast-flow.js) now also sweeps the system Summon AE via the existing `findSystemSummonAE(caster)` helper (both abort call sites pass the caster). The successful path is unaffected — the anchor funnel already owns Summon-AE teardown there.
- **Bug #10 — over-budget dialog state made unreachable, not merely rejected.** Previously a player could tick mods past the slot budget; the dialog disabled Confirm and turned the counter "over," but the over-budget state was still reachable and the counter rendered **orange** (a theme resolving `--color-text-hyperlink`), not as an error. Fixed: [`modules/cast-dialog.js`](../../../modules/cast-dialog.js) `_prepareContext` computes the remaining budget before building rows and marks any not-yet-selected mod whose cost exceeds the remainder as `disabled`; [`templates/cast-dialog.hbs`](../../../templates/cast-dialog.hbs) renders those checkboxes `disabled` and greys the row; already-selected mods stay enabled so they can be unticked. CSS in [`styles/manifest-tulpa.css`](../../../styles/manifest-tulpa.css): over-budget counter → explicit error red `#c0392b`; disabled-row rule retargeted to `.mt-row.disabled` (the old `input:disabled + label` adjacent-sibling selector never matched the `label.mt-row > input` markup). The submit-time guard stays as defense in depth.
- **Cosmetic — `ready` console log printed before the double-registration guard.** [`modules/init.js`](../../../modules/init.js) logged `manifest-tulpa | ready` at the top of the `ready` handler, so a double-load printed the line twice even though the guard then bailed. Moved the log below the `__manifestTulpaHooksRegistered` guard so it prints exactly once per genuine registration.

### 🔴 Bug #1 — Recast over a live Tulpa destroys BOTH Tulpas and silently aborts (HIGH, **regression of v0.1.13 REG-2**) — ✅ CODE-FIXED 2026-06-06 (see *Remediation Log — Pass 2* at top)

> **[2026-06-06 forward-pointer]** This bug was **fixed at the code level** in *Remediation Log — Pass 2* (top of document). **Heads-up:** the root-cause model in this section is the *as-investigated-at-smoke-time* version; the Pass 2 log **corrects it** — the *new* token actually dies via **midi-qol's** token-dependent pin to a by-name-reused "Summon:" AE (not the `findSystemSummonAE` new/old ambiguity guessed below), and the shipped fix dismisses the previous Tulpa **through the funnel in `preUseActivity`** (not the by-token disambiguation suggested below). R15/R43 remain **FAIL** here pending a live re-smoke.

**Affected rows:** R15 FAIL, R43 FAIL.

**What you'd see at the table:** a player has a Tulpa out, casts Manifest Tulpa again. Result: **zero** Tulpas on the board (the old one *and* the new one both vanish), the caster's effects panel is empty, a 5th-level slot is gone, the modification menu never opens, and two red errors appear:
- UI banner: `ActiveEffect "Vhwx0OepU5TBLeuy" does not exist!`
- Console: `EXCEPTION Error: undefined id [mfvseLvHAd21cjt5] does not exist in the EmbeddedCollection collection.`

**Root cause (code-grounded, high confidence).** The recast cascade re-enters the dismissal funnel through a path the v0.1.13 `skipFunnel` guard doesn't cover:
1. dnd5e creates the **new** Tulpa token, then fires `dnd5e.postSummon`.
2. `onPostSummon` ([cast-flow.js:57-69](../../../modules/cast-flow.js)) sees a `previous` anchor and calls `performDismissCleanup(previous)`, which deletes the **old** token.
3. Deleting the old token fires `onPreDeleteToken` ([dismiss-flow.js:104-120](../../../modules/dismiss-flow.js)), which deletes the old anchor with `{dismissReason:"manual", skipTokenTeardown:true}` — note: **`skipTokenTeardown`, not `skipFunnel`** → this **re-enters** `performDismissCleanup`.
4. The re-entrant cleanup calls `findSystemSummonAE(caster)` ([dismiss-helpers.js:10](../../../modules/dismiss-helpers.js)), which matches by spell-item origin **or** a `\bmanifest\s*tulpa\b` name regex. **The old and new summons share the same origin AND the same name**, so `.find()` cannot tell them apart and can sweep the **new** summon's AE → dnd5e tears down the **new** token too.
5. Back at [cast-flow.js:68](../../../modules/cast-flow.js), `previous.delete({skipFunnel:true})` runs — but the anchor was already deleted in step 3, so it throws the **uncaught** `undefined id … EmbeddedCollection` error (line 68 has no try/catch). `onPostSummon` aborts before `openCastDialog` → no dialog, no new anchor, no stats.

**Why the v0.1.13 fix is insufficient.** v0.1.13 added a `skipFunnel` flag so the recast branch's *own* anchor delete (line 68) wouldn't re-run the funnel. But the actual recast goes **token-delete → `onPreDeleteToken` → anchor-delete(`skipTokenTeardown`) → funnel re-entry** — a path that never sets `skipFunnel`. The guard and the `findSystemSummonAE` old/new ambiguity are the two open holes.

**Suggested fix direction (grounded in dnd5e 5.2.5 + the module's own flag namespace):**
- **Disambiguate summons by token, not by name/origin.** `findSystemSummonAE` should resolve the AE tied to the *specific* `tulpaUuid` being dismissed. In dnd5e 5.2.5 the system writes `flags.dnd5e.summon` carrying the profile/placement linkage; match the AE whose summon linkage points at the token being torn down rather than any AE whose origin/name matches the spell. The name-regex fallback should be last-resort only and scoped to "exactly one match," not `.find()`-first.
- **Make the recast pre-dismissal explicit and awaited *before* the new summon exists.** Capture and fully dismiss the previous Tulpa in `dnd5e.preUseActivity` (where the slot is already captured), so the old anchor/token/summon-AE are gone *before* dnd5e creates the new token — eliminating the old/new ambiguity window entirely. Then `onPostSummon` only ever sees a clean board.
- **Wrap line 68 in try/catch** at minimum, so an already-deleted anchor can't abort the whole cast. (This is a band-aid, not the cure — it would stop the *abort* but not the double-destroy.)

| 2 | dnd5e core | cascade-delete **Tulpa token** `XYUbojHEB5Cibbtx` | `ActiveEffect5e#_onDelete` iterates Summon AE's `getDependents()` → `MidiTokenDocument.delete` |

| 4 | times-up | delete **anchor** `V2ZGiEC0FzqbMTwH` **AGAIN** | anchor already gone at s=3 → `ActiveEffect "V2ZGiEC0FzqbMTwH" does not exist!` **(Bug #2)** |

The module's own guarded token delete (the `.has(id)` membership check in `performDismissCleanup`) never fires on this path — `skipTokenTeardown:true` was set at s=3, so the funnel skips the token block entirely. The banner is purely times-up's s=4 anchor delete hitting an already-deleted document. **The banner id is the anchor AE id, not a token id.**

> **In plain English:** times-up holds both same-duration AEs in its expiry batch. Deleting the Summon AE first cascades through dnd5e to delete the token, which triggers our hook to delete the anchor as a side-effect (s=3) — before times-up reaches the anchor in its own batch (s=4). So times-up's anchor delete finds nothing and throws. The cleanup result is completely correct; the error is pure noise.

**Fix applied (Remediation Log — Pass 3):** in `onPreDeleteToken`, when `isAnchorDurationExpired(anchor)` is true (`anchor.duration.remaining <= 0`), return immediately without deleting the anchor. times-up's s=4 anchor delete becomes the SOLE anchor delete → no double-delete → no banner (Bug #2). Because that delete carries no module options, `inferReason` step-5 returns "duration" instead of "manual" (Bug #3). A genuine GM manual delete has `remaining > 0` → guard false → old behavior unchanged.

### 🟠 Bug #5 — Missing-asset fast-skip guard is dead code (MEDIUM; this is a documented v0.1.13 behavior that never worked) — ✅ FIXED 2026-06-06 (see Remediation Log at top)

**Affected rows:** R24 FAIL, compounds R9, A6, A9.

**Root cause.** [animations.js:35-40](../../../modules/animations.js):
```js
function assetAvailable(asset) {
  const db = globalThis.Sequencer?.Database;
  if (typeof db?.entryExists !== "function") return true;
  try { return db.entryExists(asset) !== false; }   // ← bug
  catch { return true; }
}
```
In **Sequencer 3.6.11**, `Database.entryExists(asset)` returns the resolved **string key** when the asset exists and **`undefined`** when it's missing — it **never returns boolean `false`.** So `entryExists(asset) !== false` is **always true**, and the intended "skip the Sequence entirely for a missing asset" optimization is dead. Verified live: `assetAvailable("jb2a.impact.010.pinkpurple") === true` even though that asset doesn't exist. Missing assets fall through to `.play()` and rely on Sequencer's own failure + the 15 s timeout net.

> **Why this matters beyond cosmetics:** the v0.1.13 changelog explicitly claims *"Pre-flight `Sequencer.Database.entryExists` continues to short-circuit before the timeout window opens for genuinely missing assets."* That claim is **false** — the short-circuit has never functioned. This is also the root of R9's caveat: a missing dismiss asset can keep the token on the board up to the full 15 s timeout instead of being skipped instantly.

**Suggested fix direction (grounded in Sequencer 3.6.11):** the only robust truthiness test for `entryExists` (which returns string-or-undefined) is `return !!db.entryExists(asset);` or `return db.entryExists(asset) != null;`. Either restores the intended fast-skip and tightens R9's worst case from 15 s back to instant.
