### (1) What was fixed

- **Bug #8 — 5 of 12 JB2A preset asset keys did not exist in jb2a_patreon 0.8.7.** Root cause confirmed *deeper* than the report: the impacts carried an erroneous **`.010`** numbered-impact segment (`jb2a.impact.010.<colour>`) — a sub-family that ships only `[blue, green, orange, purple, red]`, so the spell's intended **yellow** and **pinkpurple** never existed there. The 3 strikes appended a non-existent `.<colour>` layer to the terminal `jb2a.unarmed_strike.magical` entry.
- **Bug #5 — the missing-asset fast-skip guard (`assetAvailable`) was dead code.** Sequencer 3.6.11 `entryExists` returns a **string key** when present and **`undefined`** when missing — never boolean `false` — so the old `!== false` test was *always true* and the guard never skipped a missing asset. That is precisely what let the missing impacts reach `.play()` and throw the detached `baseTexture` rejection that `try/catch` + `withTimeout` cannot see.

### 🔴 Bug #1 — Recast over a live Tulpa destroys BOTH Tulpas and silently aborts (HIGH, **regression of v0.1.13 REG-2**)

**Affected rows:** R15 FAIL, R43 FAIL.

**What you'd see at the table:** a player has a Tulpa out, casts Manifest Tulpa again. Result: **zero** Tulpas on the board (the old one *and* the new one both vanish), the caster's effects panel is empty, a 5th-level slot is gone, the modification menu never opens, and two red errors appear:
- UI banner: `ActiveEffect "Vhwx0OepU5TBLeuy" does not exist!`
- Console: `EXCEPTION Error: undefined id [mfvseLvHAd21cjt5] does not exist in the EmbeddedCollection collection.`

**Root cause (code-grounded, high confidence).** The recast cascade re-enters the dismissal funnel through a path the v0.1.13 `skipFunnel` guard doesn't cover:
1. dnd5e creates the **new** Tulpa token, then fires `dnd5e.postSummon`.
2. `onPostSummon` ([cast-flow.js:57-69](../../../modules/cast-flow.js)) sees a `previous` anchor and calls `performDismissCleanup(previous)`, which deletes the **old** token.
3. Deleting the old token fires `onPreDeleteToken` ([dismiss-flow.js:104-120](../../../modules/dismiss-flow.js)), which deletes the old anchor with `{dismissReason:"manual", skipTokenTeardown:true}` — note: **`skipTokenTeardown`, not `skipFunnel`** → this **re-enters** `performDismissCleanup`.
4. The re-entrant cleanup calls `findSystemSummonAE(caster)` ([dismiss-helpers.js:10](../../../modules/dismiss-helpers.js)), which matches by spell-item origin **or** a `\bmanifest\s*tulpa\b` name regex. **The old and new summons share the same origin AND the same name**, so `.find()` cannot tell them apart and can sweep the **new** summon's AE → dnd5e tears down the **new** token too.
5. Back at [cast-flow.js:68](../../../modules/cast-flow.js), `previous.delete({skipFunnel:true})` runs — but the anchor was already deleted in step 3, so it throws the **uncaught** `undefined id … EmbeddedCollection` error (line 68 has no try/catch). `onPostSummon` aborts before `openCastDialog` → no dialog, no new anchor, no stats.

**Why the v0.1.13 fix is insufficient.** v0.1.13 added a `skipFunnel` flag so the recast branch's *own* anchor delete (line 68) wouldn't re-run the funnel. But the actual recast goes **token-delete → `onPreDeleteToken` → anchor-delete(`skipTokenTeardown`) → funnel re-entry** — a path that never sets `skipFunnel`. The guard and the `findSystemSummonAE` old/new ambiguity are the two open holes.

**Suggested fix direction (grounded in dnd5e 5.2.5 + the module's own flag namespace):**
- **Disambiguate summons by token, not by name/origin.** `findSystemSummonAE` should resolve the AE tied to the *specific* `tulpaUuid` being dismissed. In dnd5e 5.2.5 the system writes `flags.dnd5e.summon` carrying the profile/placement linkage; match the AE whose summon linkage points at the token being torn down rather than any AE whose origin/name matches the spell. The name-regex fallback should be last-resort only and scoped to "exactly one match," not `.find()`-first.
- **Make the recast pre-dismissal explicit and awaited *before* the new summon exists.** Capture and fully dismiss the previous Tulpa in `dnd5e.preUseActivity` (where the slot is already captured), so the old anchor/token/summon-AE are gone *before* dnd5e creates the new token — eliminating the old/new ambiguity window entirely. Then `onPostSummon` only ever sees a clean board.
- **Wrap line 68 in try/catch** at minimum, so an already-deleted anchor can't abort the whole cast. (This is a band-aid, not the cure — it would stop the *abort* but not the double-destroy.)

### 🔴 Bug #2 — `undefined id … EmbeddedCollection` red banner on every duration-expiry dismissal (HIGH)

**Affected rows:** R23 FAIL, R43 (same error family).

**What you'd see:** a Tulpa's hour runs out. Everything actually cleans up (token gone, anchor gone, summon AE swept, caster effects empty) — **but** a red banner fires: `undefined id [<tokenId>] does not exist in the EmbeddedCollection collection.`

**Root cause.** This is a **token double-delete race**. When `times-up` expires the anchor's duration, the token gets deleted by dnd5e's summon lifecycle and/or times-up *first*, which fires `onPreDeleteToken` → the anchor is deleted with `skipTokenTeardown:true`. But on the duration path the funnel **also** issues a `tokenDoc.delete()`. The module guards *its own* delete ([dismiss-flow.js:78-82](../../../modules/dismiss-flow.js): `.has(id)` check + try/catch → would log "token delete failed," not a red banner). So the **uncaught** throw comes from **outside** the module — times-up and/or dnd5e's summon cleanup racing the funnel; whichever loses the race calls `EmbeddedCollection.get` on an id that's already gone → red banner.

**Why manual (R27) and zeroHP (R26/R16) are clean and duration/recast aren't:** the clean paths set `skipTokenTeardown:true`, so the funnel issues **zero** `tokenDoc.delete()` calls — nothing races the external deleter. Duration and recast let the funnel *also* delete the token, creating the race. This is the unifying root cause across Bug #1 and Bug #2.

> **In plain English:** two different parts of Foundry both try to remove the same token at the same time. One of them gets there first; the second trips over the now-missing token and yells. The cleanup result is correct — it's just noisy and alarming.

**Suggested fix direction (grounded in times-up 13.1.9 + dnd5e 5.2.5 summon lifecycle):** a single dismissal should own token teardown **exactly once.** Two viable shapes:
- **Debounce/lock the funnel per `tulpaUuid`.** Once any trigger begins teardown for a given Tulpa, mark it (e.g. a module-local `Set` of in-flight `tulpaUuid`s) so subsequent re-entries (the second deleter) become no-ops instead of issuing a competing delete.
- **Never have the funnel delete the token when the trigger is itself a token/AE deletion.** Generalize the `skipTokenTeardown` policy: if the dismissal originated from times-up's AE expiry (which dnd5e ties to its own token teardown), let dnd5e own the token delete and have the funnel only sweep the summon AE + post the card. The funnel should only issue `tokenDoc.delete()` for triggers that *don't* already delete the token (Tulpa-0-HP via the HP watcher).

### 🟠 Bug #3 — Duration-expiry posts the WRONG dismissal reason (MEDIUM)

**Affected row:** R23.

**What you'd see:** when a Tulpa times out, the chat card reads *"The Tulpa fades — the Tulpa's token was deleted"* (the **manual** reason) instead of a **duration** reason.

**Root cause.** On the duration path the token is deleted first → `onPreDeleteToken` stamps `dismissReason:"manual"` ([dismiss-flow.js:119](../../../modules/dismiss-flow.js)). When the funnel re-enters, `inferReason` step 1 trusts that option-supplied `"manual"` and returns early — **shadowing** the step-5 check that would have noticed `anchor.duration.remaining <= 0` and returned `"duration"`.

**Suggested fix direction:** in `inferReason`, check `anchor.duration.remaining <= 0` (or a times-up-expiry signal) **before** trusting an option `dismissReason:"manual"` — a duration-driven token delete shouldn't masquerade as a manual one. Alternatively, have `onPreDeleteToken` *not* stamp `"manual"` when the token delete was itself system/duration-driven (detectable because the anchor's duration has already elapsed). Note these are the same code paths as Bug #2 — fixing the ownership race naturally creates the right place to fix the reason.

### 🟠 Bug #4 — `isDeath` is an invalid DAE specialDuration → status-toggle death doesn't dismiss (MEDIUM)

**Affected row:** R18 (caveat).

**What you'd see:** if a caster is marked **Dead** by status toggle *without* their HP hitting 0 (homebrew save-or-die, GM narrative toggle, an instant-kill that flags Dead but doesn't zero HP), the Tulpa is **not** dismissed.

**Root cause.** The anchor's `dae` flag is `{showIcon:false, specialDuration:["zeroHP","isDeath"]}` (set at [cast-flow.js:273](../../../modules/cast-flow.js)). In **dae 13.0.26**, `DAE.daeSpecialDurations()` contains `zeroHP` but **not** `isDeath` — so that entry is a silent **no-op**. The canonical death path (HP→0) works flawlessly because the valid `zeroHP` key fires (R18 leg B = PASS, correct "the caster died" card). Only the pure status-toggle path is dead.

> **Nuance for D&D:** a *player* character at 0 HP goes **unconscious + death saves**, not "Dead" status — so a PC dropping to 0 HP dismisses via `zeroHP` and posts the *casterZeroHP* card, which is correct. The gap only bites a caster flagged Dead without an HP change.

**Suggested fix direction (grounded in dae 13.0.26):** either (a) drop the dead `"isDeath"` entry and rely on `zeroHP` (covers all HP-driven deaths), accepting that a pure status toggle won't auto-dismiss; or (b) add an explicit listener on the caster's "dead" status application (a dnd5e status/`createActiveEffect` hook) that deletes the anchor with `dismissReason:"isDeath"`. **Validate any specialDuration string against `DAE.daeSpecialDurations()` before shipping** — that's the check that would have caught this.

### 🟠 Bug #5 — Missing-asset fast-skip guard is dead code (MEDIUM; this is a documented v0.1.13 behavior that never worked) — ✅ FIXED 2026-06-06 (see Remediation Log at top)

**Affected rows:** R24 FAIL, compounds R9, A6, A9.

**Root cause.** [animations.js:35-40](../../../modules/animations.js):
```js
function assetAvailable(asset) {
  const db = globalThis.Sequencer?.Database;
  if (typeof db?.entryExists !== "function") return true;
  try { return db.entryExists(asset) !== false; }   // ← bug
  catch { return true; }
}
```
In **Sequencer 3.6.11**, `Database.entryExists(asset)` returns the resolved **string key** when the asset exists and **`undefined`** when it's missing — it **never returns boolean `false`.** So `entryExists(asset) !== false` is **always true**, and the intended "skip the Sequence entirely for a missing asset" optimization is dead. Verified live: `assetAvailable("jb2a.impact.010.pinkpurple") === true` even though that asset doesn't exist. Missing assets fall through to `.play()` and rely on Sequencer's own failure + the 15 s timeout net.

> **Why this matters beyond cosmetics:** the v0.1.13 changelog explicitly claims *"Pre-flight `Sequencer.Database.entryExists` continues to short-circuit before the timeout window opens for genuinely missing assets."* That claim is **false** — the short-circuit has never functioned. This is also the root of R9's caveat: a missing dismiss asset can keep the token on the board up to the full 15 s timeout instead of being skipped instantly.

**Suggested fix direction (grounded in Sequencer 3.6.11):** the only robust truthiness test for `entryExists` (which returns string-or-undefined) is `return !!db.entryExists(asset);` or `return db.entryExists(asset) != null;`. Either restores the intended fast-skip and tightens R9's worst case from 15 s back to instant.

### 🟠 Bug #6 — Orphan combatant left in the tracker after every dismissal (MEDIUM)

**Affected:** observed on **all four** exercised dismissal paths (duration, manual, death, zeroHP).

**What you'd see:** after a Tulpa is dismissed during combat, the combat tracker still lists a "Tulpa" combatant with no token behind it (`hasToken:false`).

**Root cause.** `performDismissCleanup` deletes the anchor, the token, and the summon AE, and posts the card — but does **no combatant cleanup** on any trigger. The initiative code (`alignTulpaInitiative`) *inserts* a combatant on a mid-combat cast but nothing *removes* it on dismissal.

**Suggested fix direction:** in `performDismissCleanup`, after the token is resolved/deleted, find the combatant whose `tokenId` matches the dismissed token (or whose actor is the synthetic Tulpa) in `game.combats` and delete it. Guard for "no active combat." This mirrors the existing single-funnel philosophy (invariant 1) — every dismissal trigger already routes through this one function, so one cleanup here covers all five triggers.

### 🟠 Bug #7 — "No-anchor" state hygiene gap: cancelled cast orphans the dnd5e summon AE (MEDIUM)

**Affected rows:** R37 (the abort contract itself PASSES; this is the side gap).
