## Executive Summary

v0.1.9 merged `setStrikeDamageType` and `empoweredStrikes.patch` into a single-writer function (`applyStrikeChanges`) to fix the v0.1.8 write-race. The merge was the right architectural call, but the implementation has a new bug: `deepClone` converts dnd5e 5.2.5's `Set`-typed `DamageData.types` into a plain object, and the full-parts-array update path (`system.activities.X.damage.parts = [...]`) is silently rejected by the data model. The net result is that the base damage type *still* never changes from bludgeoning, just for a different reason than v0.1.8.

Three items regressed from v0.1.8, two new bugs were discovered, and several previously untested areas were exercised for the first time. The dismissal pipeline has structural issues (token orphans, incorrect dismiss-reason text) that were not visible in v0.1.8's code-only review.

### R8: Damage Type on Manifestation Strike -- FAIL (BLOCKING)

**What should happen:** When you pick a damage type (e.g., radiant) in the cast dialog, the Manifestation Strike weapon should deal that type instead of bludgeoning.

**What actually happens:** Both Melee and Ranged activities still show `types: ["bludgeoning"]` after casting with radiant selected.

**Why it fails:** In `cast-flow.js` line 139, the `applyStrikeChanges` function builds its update like this:

```
update[`system.activities.${actId}.damage.parts`] = parts;
```

The `parts` array is created via `foundry.utils.deepClone(act.damage?.parts ?? [])`. In dnd5e 5.2.5, the `types` field inside each damage part is a JavaScript `Set` (not a plain array). When `deepClone` copies it, the Set becomes a plain object (`{0: "bludgeoning"}`). The data model then silently rejects the entire update because it expects a Set or an array, not an object.

**Manual verification:** Setting the damage type via dot-notation works:

```
update[`system.activities.${actId}.damage.parts.0.types`] = ["radiant"];
```

This bypasses the deepClone issue because it sends a plain array directly to the specific field, which dnd5e coerces into a Set correctly.

**Change from v0.1.8:** In v0.1.8, there were two separate functions (`setStrikeDamageType` and the Empowered Strikes patch) that raced each other, with the second write clobbering the first. v0.1.9 correctly merged these into a single-writer function (`applyStrikeChanges`), but the deepClone/Set incompatibility means the merged write itself fails. Different root cause, same symptom.

## Bugs Found

### Bug 1: applyStrikeChanges deepClone/Set Silent Failure (BLOCKING)

**Severity:** Critical
**Affects:** R8, R20, R25 (every cast since v0.1.9, and likely v0.1.8 too)
**File:** `cast-flow.js` lines 128-142
**New in v0.1.9?** New root cause, but the symptom (damage type stuck on bludgeoning) existed in v0.1.8 with a different cause (write race).

**Plain-English explanation:** When you pick "radiant" in the cast dialog, the module tries to update the Manifestation Strike weapon to deal radiant damage. It does this by copying the weapon's damage data, changing the type to radiant, and saving the copy back. The problem is that dnd5e stores the damage type in a special JavaScript data structure called a Set, and the copy function (`deepClone`) doesn't know how to copy Sets properly. It turns the Set into a plain object. When the module tries to save this mangled copy back to the weapon, dnd5e looks at it, doesn't recognize the format, and silently ignores the update. The weapon stays bludgeoning.

**Suggested fix (research-supported):**

Replace the full-parts-array update with dot-notation updates that target each field individually. This was manually verified during testing:

```javascript
// Instead of:
update[`system.activities.${actId}.damage.parts`] = parts;

// Use dot-notation for the types field:
if (parts.length && parts[0].types) {
  update[`system.activities.${actId}.damage.parts.0.types`] = Array.from(parts[0].types);
}
// For Empowered Strikes (Part 1 addition), use createEmbeddedDocuments or
// a separate dot-notation path for the new part.
```

The key insight is that dnd5e 5.2.5's `DamageData` model will accept a plain array `["radiant"]` via dot-notation and coerce it into a Set internally, but it rejects a full parts-array replacement where the types field is a mangled Set-turned-object.

**Alternative approach:** Instead of `deepClone`, build a fresh parts array from scratch using only plain JavaScript types:

```javascript
const freshParts = (act.damage?.parts ?? []).map(p => ({
  ...p,
  types: Array.isArray(p.types) ? [...p.types] : [...(p.types ?? [])]
}));
```

This ensures types is always a plain array, which dnd5e will accept.

### Bug 2: Token Orphan on zeroHP Dismiss (HIGH)

**Severity:** High
**Affects:** R16, R17
**File:** `dismiss-flow.js` (token cleanup section)
**New in v0.1.9?** First time tested at runtime. May have existed in v0.1.8 (untested there).

**Plain-English explanation:** When the Tulpa hits 0 HP, the module correctly deletes the anchor effect from the caster, which triggers the dismiss cascade. The cascade tries to play a "dismiss" animation and then delete the Tulpa's token from the map. But the dismiss animation fails (because of an invalid animation asset, see Bug 5), and after the animation times out, the token deletion still doesn't happen. The Tulpa's token sits on the map as an orphan with no connection to anything.

**Suggested fix:** The token deletion should not depend on animation success. Wrap the animation call in a try/catch or use a `.finally()` block to ensure `tokenDoc.delete()` runs regardless of animation outcome:

```javascript
try {
  await playDismiss(token, damageType);
} catch (err) {
  console.warn(`${MODULE_ID} | dismiss animation failed:`, err);
} finally {
  if (tokenDoc?.parent?.tokens?.get?.(tokenDoc.id) === tokenDoc) {
    await tokenDoc.delete();
  }
}
```

### Bug 3: Wrong Dismiss Reason on zeroHP (MEDIUM)

**Severity:** Medium (incorrect user-facing text)
**Affects:** R16, R17
**File:** `dismiss-flow.js` or `chat-cards.js` (reason-to-text mapping)
**New in v0.1.9?** First time tested at runtime.

**Plain-English explanation:** When the Tulpa hits 0 HP, the chat card says "the caster fell to 0 HP." This is wrong. The *Tulpa* fell to 0 HP, not the caster. The module uses "zeroHP" as the dismiss reason for both cases (Tulpa at 0 HP via the HP watcher, and caster at 0 HP via DAE's specialDuration), and the text template maps "zeroHP" to a caster-focused message.

**Suggested fix:** Use distinct reason codes for the two cases:
- `"tulpaZeroHP"` when the HP watcher detects the Tulpa at 0 HP
- `"casterZeroHP"` when DAE's specialDuration fires on the caster

Then map each to the correct chat text:
- `"tulpaZeroHP"` -> "the Tulpa was reduced to 0 hit points"
- `"casterZeroHP"` -> "the caster fell to 0 hit points"

### Bug 4: Async preUpdateActor Hook Race (MEDIUM, LATENT)

**Severity:** Medium (race condition, not always triggered)
**Affects:** R17, R26
**File:** `tulpa-hp-watcher.js` lines 15-42
**New in v0.1.9?** No, identified in v0.1.8 and not yet fixed.

**Plain-English explanation:** When the Tulpa takes lethal damage with Relentless active, the module intercepts the HP change and clamps it to 1. It also needs to record "I already used Relentless" so it doesn't clamp again on the next hit. The problem is that the "record" step (`setFlag`) is an asynchronous database write inside a hook that Foundry calls synchronously. Foundry calls the hook, gets back a Promise, and throws it away. The HP clamp works because it modifies the pending update object directly (synchronous). But the flag write is a separate database operation that may or may not complete before Foundry moves on. If the page reloads or another update happens before the flag write finishes, the flag is lost and Relentless could trigger twice.

**Suggested fix (from v0.1.8 report, still valid):** Piggyback the flag onto the same update Foundry is already processing:

```javascript
foundry.utils.setProperty(changes, "flags.manifest-tulpa.relentlessUsed", true);
```

This is synchronous and rides the same `updateActor` call, eliminating the race entirely.

### Bug 5: Invalid JB2A Asset `jb2a.impact.010.pink` (MEDIUM, REGRESSION)

**Severity:** Medium (causes animation failures + 5s delay)
**Affects:** R24, R9, R16, R17
**File:** `animations.js` (dismiss animation asset key)
**New in v0.1.9?** REGRESSION. v0.1.8 confirmed the `assetAvailable()` pre-flight was working (code-level review). In v0.1.9, the dismiss animation uses `jb2a.impact.010.pink`, which does not exist in the JB2A Patreon 0.6.91 database.

**Plain-English explanation:** When the Tulpa is dismissed, the module tries to play a pink impact animation. The animation asset key it uses (`jb2a.impact.010.pink`) doesn't exist in the installed JB2A animation library. The pre-flight check (which is supposed to detect missing assets and skip the animation) either isn't running for this path or isn't catching this specific key. Sequencer tries to play it, fails, and hangs for 5 seconds before timing out. This delay compounds with Bug 2 (token orphan) because the token deletion may be waiting on the animation to finish.

**Suggested fix:**
1. Verify the correct JB2A asset key for the intended animation (browse the Sequencer database browser in Foundry to find the right path).
2. Ensure `assetAvailable()` is called before `playDismiss()` -- add logging to confirm the pre-flight runs.
3. Consider using a known-good fallback asset (e.g., `jb2a.impact.004.dark_red`) when the primary asset is missing.

### Bug 6: ManifestTulpaCastDialog._updatePosition TypeError (LOW)

**Severity:** Low (cosmetic, can cause ghost casts in edge cases)
**Affects:** R4
**File:** `cast-dialog.js` (_updatePosition method)
**New in v0.1.9?** No, present in v0.1.8 (triggered by BBMM interruption).

**Plain-English explanation:** The cast dialog tries to position itself on screen by reading the width of its HTML element. If other windows or tooltips are overlapping, the element reference can be null, causing a "Cannot read properties of null (reading 'offsetWidth')" error. This usually just causes a console error, but in some cases it can cause the cast flow to run without showing the dialog, producing a Tulpa that immediately dismisses with no feedback to the player.

**Suggested fix:** Add a null guard in `_updatePosition`:

```javascript
_updatePosition() {
  if (!this.element?.[0]) return;
  // ... existing positioning logic
}
```

## Recommendations for v0.1.10

### Priority 1: Fix Bug 1 (deepClone/Set in applyStrikeChanges)

This is the only BLOCKING issue. The single-writer architecture is sound. The fix is to avoid passing deepCloned DamageData through the full-parts-array update path. Two options:

**Option A (minimal change):** Use dot-notation for the types field:
```javascript
update[`system.activities.${actId}.damage.parts.0.types`] = [castConfig.damageType];
```

**Option B (robust):** Build fresh parts arrays using only plain types, never deepClone:
```javascript
const freshTypes = [castConfig.damageType];
// ... build parts without deepClone, or clone manually with Set-to-Array conversion
```

Test both: (a) damage type only, and (b) damage type + Empowered Strikes.

### Priority 2: Fix Bug 2 (token orphan on dismiss)

Ensure token deletion runs regardless of animation outcome. Use try/finally around the animation call. This is critical for gameplay because orphaned tokens confuse the map.

### Priority 3: Fix Bug 5 (invalid JB2A asset key)

Find the correct asset path for the dismiss animation via Sequencer's database browser. Update the key in `animations.js`. Verify that `assetAvailable()` is being called on the dismiss path.

### Priority 4: Fix Bug 3 (wrong dismiss reason text)

Use distinct reason codes for Tulpa zeroHP vs caster zeroHP. Small change with high user-facing impact.

### Priority 5: Fix Bug 4 (async preUpdateActor race)

One-line fix: replace `await actor.setFlag(...)` with `foundry.utils.setProperty(changes, "flags.manifest-tulpa.relentlessUsed", true)`. This was recommended in v0.1.8 and is still the correct approach.

### Priority 6: Investigate R21 regression (aura propagation)

Since the aura AE data is structurally identical to v0.1.8, the regression is likely environmental. Check whether the dependency version changes (especially sequencer 3.4.3 vs 3.6.11) affect Aura Effects' collision detection timing. Test with the v0.1.8 dependency versions if possible.

### Priority 7: Guard _updatePosition (Bug 6)

Add a null check in `ManifestTulpaCastDialog._updatePosition`. Low priority but prevents the occasional ghost-cast scenario.
