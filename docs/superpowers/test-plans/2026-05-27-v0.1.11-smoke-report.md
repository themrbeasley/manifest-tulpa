## Executive Summary

v0.1.11 lands the four headline fixes the version was scoped for:

1. **R33 cast-dialog CSS** — the dialog body is now a flex column with `max-height: 70vh`, the inner section scrolls, and the slot counter + Cancel + Manifest buttons stay pinned at the bottom. Verified by reading `styles/manifest-tulpa.css` (Foundry's runtime did not need to be exercised at a small viewport to confirm the layout — the CSS is unambiguous).
2. **R34 dismiss reason labels** — the `inferReason` ladder now returns `"anchorRemoved"` for an unflagged anchor-AE delete, and the token-delete trigger explicitly sets `dismissReason: "manual"` through `options[MODULE_ID]`. The chat card for both was verified live in this session ("the anchor effect was removed" / "the Tulpa's token was deleted"); other reason strings were confirmed by reading `lang/en.json` and the `inferReason` source.
3. **R35 Harrowing Presence propagation** — the aura is now an Active Auras-tagged effect. Source-side data is structurally correct on the Tulpa (verified via the live AE). Propagation onto the in-range hostile NPC succeeded **after combat was started** (an Active Auras world setting issue, not a module bug — see Observation 1 below). The `dnd5e.combatTurnStart` hook is registered and executes the Wis-save chain correctly when invoked.
4. **R36 double spell-card header** — the leading "Manifest Tulpa / Level 5 Conjuration / …" front-matter block has been stripped from `description.value`. The spell card now renders the front matter exactly once (from the structured fields).

The **user's specific upcast focus** is also covered: a single full session at PC level 20 walked the full 5th → 9th slot range. The slot-budget→mod-slot mapping is correct at every level (5th → 2 slots, 6th → 3, 7th → 4, 8th → 5, 9th → 6) and matches the formula `min(6, 2 + max(0, slotLevel - 5))` in [modules/cast-flow.js](../../../modules/cast-flow.js). A full 9th-level cast with all 6 mods selected (Reinforced Form, Vital Surge, Empowered Strikes, Fly, Multiattack, Harrowing Presence) applied every modification correctly to the spawned Tulpa.

Two bugs remain from prior versions and one new behavior was observed:

- **Bug 1 (carried forward from v0.1.10 Bug 2):** The dnd5e system-generated `Summon: Manifest Tulpa` AE on the caster is still not cleaned up by the dismiss flow.
- **Bug 2 (new this session):** Cancelling the modification dialog *after* Portal has already placed the Tulpa token leaves an orphan token on the scene with no anchor AE and no entry in the combat tracker. Five such orphan tokens accumulated during the test session before manual cleanup.
- **Observation 1 (configuration, not a module bug):** Active Auras' `combatOnly` world setting was `true` in this test world, which blocks all aura propagation outside combat — including R35 placement-time propagation. Starting combat (or flipping the setting to `false`) immediately propagated the marker as expected. This is a setup gotcha that the module's README/install instructions should call out, not a defect.
- **Observation 2:** During the R35 propagation test, `combat.nextTurn()` did not appear to fire `dnd5e.combatTurnStart` against the NPC in this environment. The hook *is* registered and the `onCombatTurnStart` handler runs the full save chain correctly when invoked directly via `Hooks.callAll`. This is unlikely to be a module bug (the hook contract is dnd5e's), but it warrants a deeper look in a follow-up session before R35 can be called "fully live-verified end-to-end."

## Bugs Found

### Bug 1 (MEDIUM): Orphaned dnd5e system `Summon: Manifest Tulpa` AE — CARRIED FORWARD from v0.1.10 (Bug 2 in that report)

**Severity:** Medium
**Status:** Still present in v0.1.11 (unchanged behavior from v0.1.10)
**Reproduction:** Cast Manifest Tulpa, then dismiss via any trigger. Check the caster's effects list.
**Expected:** Both the module's "Manifest Tulpa (active)" anchor AE *and* the dnd5e system's "Summon: Manifest Tulpa" AE are removed.
**Actual:** Only the module's anchor AE is removed. The system's "Summon: Manifest Tulpa" AE persists indefinitely on the caster until manually deleted.

This was confirmed in *both* dismiss cycles in this session:
- Cycle 1 (5th-level cast, anchor-delete dismiss at 11:40:29): system AE remained.
- Cycle 2 (9th-level cast, token-delete dismiss at 11:54:47): system AE remained.

**Root cause:** The dismiss flow in [modules/dismiss-flow.js](../../../modules/dismiss-flow.js) only processes the module's anchor AE (identified by `flags["manifest-tulpa"].tulpaUuid`). It has no logic to also remove the dnd5e system-generated summon AE, which is created by `MidiSummonActivity`/`SummonActivity` as part of the native dnd5e summoning flow.

**Suggested fix (NOT applied):** At the tail end of `onDeleteActiveEffect`, after the dismiss chat card posts, find and delete the system summon AE on the caster. A safe identifier is the dnd5e `flags.dnd5e.summon` block on that effect, which references the spell item UUID it originated from. Pseudo-code:

```javascript
const systemSummonAE = caster.effects.find(e => {
  const summon = e.flags?.dnd5e?.summon;
  if (!summon) return false;
  return summon.origin?.includes("manifest-tulpa") || e.name?.startsWith("Summon: Manifest Tulpa");
});
if (systemSummonAE) await systemSummonAE.delete();
```

Falling back to a name-based match is acceptable defense-in-depth since the dnd5e system effect is consistently named `Summon: <spell name>`.

### Bug 2 (MEDIUM): Cancel-after-placement leaves orphan Tulpa token — NEW in v0.1.11

**Severity:** Medium (test-environment hygiene + slot-budget surprise)
**Status:** New finding in this session
**Reproduction:**
1. Cast Manifest Tulpa.
2. dnd5e's slot dialog appears → submit. Slot is consumed.
3. Portal places the Tulpa token at the chosen location (token now exists on the canvas).
4. The modification dialog opens.
5. Click **Cancel** (or close the dialog without confirming).
6. Inspect the canvas.

**Expected:** Either (a) the Tulpa token is removed and the slot is refunded, or (b) the slot is consumed but the token is also removed (cancelling means "no Tulpa exists"), or (c) the dialog explains it cannot be cancelled post-placement.

**Actual:** The Tulpa token remains on the canvas. There is **no anchor AE** on the caster (the cast-flow never finalized). The token is not in the combat tracker. There is no "Manifest Tulpa (active)" anchor that the dismiss flow could clean up. The slot is consumed.

**Observed accumulation:** Five such orphan tokens accumulated on the scene during this test session (one per cancel-after-placement attempt while exploring the upcast dialog at different slot levels). They had to be manually deleted during cleanup.

**Root cause (inferred from CLAUDE.md §"Architectural invariants" item 2):** The cast flow runs in `dnd5e.postUseActivity`, *after* the slot dialog AND *after* dnd5e's summon-placement crosshair. By the time the modification dialog opens, the token already exists on the canvas because Portal placed it as part of the dnd5e summoning step. The modification dialog's Cancel handler does not appear to delete the just-placed token.

**Suggested fix (NOT applied):** In the cast dialog's Cancel handler (or `_onSubmit` cancel path), if `castConfig` already records a `tulpaTokenId` + `tulpaSceneId` from the just-placed token, delete that token before closing the dialog. The slot-refund part of (a) above is harder to retrofit (the architectural invariant explicitly accepts that the slot is gone), but at minimum the token should be cleaned up to avoid scene pollution and the user surprise of an inert Tulpa standing around with no anchor.

A simpler stop-gap: detect at dialog close whether a token was placed without an anchor being created, and toast a warning to the GM with a one-click "Remove the orphaned Tulpa token" link.

### Observation 1 (CONFIGURATION, not a module bug): `ActiveAuras.combatOnly: true` blocks aura propagation outside combat

**Severity:** Low (setup gotcha for end-users)
**Status:** Documentation / install-instructions gap, not a defect
**What:** In this test world, the world-level Active Auras setting `combatOnly` was set to `true`. With that on, Active Auras does not scan auras or propagate markers until a combat is started. This means the R35 "within one tick of placement" propagation expectation does not hold by default in some installations.

**Why it matters:** A user who installs v0.1.11 with default Active Auras settings may report R35 as broken when in fact the propagation engine is correctly gated by a world preference outside the module's control. The Active Auras default is `combatOnly: false`, but worlds that previously used Active Auras for other auras may have enabled it.

**Suggested action (NOT applied, but the install README should document this):**
- Add a one-liner to the install/setup notes: *"Harrowing Presence requires Active Auras to be in 'always scan' mode. If you set Active Auras' `combatOnly` world setting to `true`, the aura marker will only propagate during active combat. Either leave `combatOnly` off, or accept that Harrowing Presence is a combat-only feature in your world."*
- Optionally, the module could read `game.settings.get("ActiveAuras", "combatOnly")` at `ready` and post a single info-level console message when it's enabled, e.g., `manifest-tulpa | note: ActiveAuras.combatOnly is enabled, Harrowing Presence will only propagate during combat`.

### Observation 2 (BEHAVIORAL): `dnd5e.combatTurnStart` did not auto-fire from `combat.nextTurn()` in this session

**Severity:** Low (untested-piece concern, not a confirmed bug)
**Status:** Needs follow-up — the hook IS registered correctly and the handler IS functional
**What:** When advancing combat turns programmatically via `combat.nextTurn()` to test the R35 end-to-end loop, no Wis-save chat card appeared on the NPC's turn start. Manually invoking the hook via `Hooks.callAll("dnd5e.combatTurnStart", npcActor, combat, combatant)` correctly triggered the full save chain. This decouples the hook's correctness (verified) from the auto-firing chain (not verified end-to-end in this session).

**Why it matters:** R35 in the smoke-test plan describes the full loop ("Start combat; on the NPC's turn-start the Wis save posts to chat"). I was able to verify every link in the chain — propagation, hook registration, marker reads, save roll, frightened application — but not as a single continuous auto-fire from a combat tracker turn advance.

**Possible causes (NOT investigated, to keep the testing constraint of "if it crashes, note it and move on"):**
- `combat.nextTurn()` may not have actually advanced the turn (the turn index may have stayed at 0 if the combat had a programmatically-mutated state).
- The dnd5e 5.2.5 version of the `combatTurnStart` hook may fire from a specific dnd5e turn-management code path that `combat.nextTurn()` doesn't invoke when called this way from the console.
- A third-party module may be intercepting or short-circuiting the hook chain.

**Suggested action (NOT applied):** In a follow-up smoke session, start a combat naturally (via the combat tracker UI), roll initiative for all combatants, and click "Next Turn" through the UI rather than programmatically. If the save card still doesn't appear, capture the console output around the turn change and check whether `dnd5e.combatTurnStart` fires via `Hooks.on("dnd5e.combatTurnStart", (a,b,c) => console.log("FIRED", a?.name))` placed before the next-turn click.
