## Bugs found

### REG-1 (CRITICAL, NEW in v0.1.12) — `dnd5e.postUseActivity` HOOK3 silently fails to fire

**Severity:** CRITICAL (blocks all spell behavior)
**Status:** OPEN — no fix attempted (per user constraint)

**Repro:**
1. Load world "Patreon Map Building" with v0.1.12 installed
2. Select character with Manifest Tulpa prepared
3. Cast Manifest Tulpa via any of:
   - Click spell name in character sheet → "Cast Spell" button on chat card → "Summon" button on chat card
   - `actor.items.find(i => i.system.identifier === "manifest-tulpa").use()`
   - `await spell.use({ configure: false })`

**Expected:** Cast dialog opens, mod selection presented, Tulpa placed via portal-lib, anchor AE created on caster, system "Summon: Manifest Tulpa" AE created on caster.

**Actual:**
- Spell slot consumed (e.g. 3rd-level slot 3 → 2)
- No dialog opens
- No Tulpa placed
- No anchor AE created
- No console error or warning
- HOOK3 (the `onPostUseActivity` callback registered at [init.js:19](../../../modules/init.js#L19)) is **never invoked** — proven by wrapping it with diagnostic `MT-WRAP` logging that never fires across three consecutive cast attempts

**Evidence (post-summon snapshot after a cast attempt):**
```
MT-POST-SUMMON: {"tokens":[{"name":"Player Character","x":0,"y":0}],"dlgs":[],"slots":2,"aes":["Savage Attacks","Benevolence (Greater)"]}
```
Slots dropped from 3 to 2 (slot consumed). No Tulpa token on the scene. No cast dialog open. No new AE on the caster. And the MT-WRAP wrapper around HOOK3 logged **no fire at all**.

**Root cause hypothesis (in priority order):**
1. The activity-type or identifier gate at [cast-flow.js:17-19](../../../modules/cast-flow.js#L17-L19) may be rejecting the cast: `if (activity?.type !== "summon") return;` followed by `if (activity.item?.system?.identifier !== SPELL_IDENTIFIER) return;`. If the compendium import landed the spell with `system.identifier` missing or with `activity.type` something other than `"summon"`, both gates would early-return silently.
2. dnd5e 5.2.5's `postUseActivity` payload shape may differ from what cast-flow expects, causing optional chaining to short-circuit.
3. The hook registration itself may be failing silently in `init.js` if the guard at `globalThis.__manifestTulpaHooksRegistered` is being set elsewhere before the `Hooks.on` calls execute.

**Suggested fix (NOT applied):**
1. Add temporary logging at the very top of `onPostUseActivity` — before any early returns — capturing `activity.type`, `activity.item?.system?.identifier`, `activity.constructor?.name`, and `usageConfig`
2. Cast the spell once in a live world; read the logged values to determine which gate is rejecting (or whether the callback is reached at all)
3. If the callback is never reached, inspect `Hooks.events["dnd5e.postUseActivity"]` to confirm HOOK3 is actually present in the listener array
4. If the gate is rejecting, fix at the source: regenerate the spell activity in `_source/` JSON with the correct `type` and `system.identifier`, then `npm run scrub && npm run build:packs`

### REG-2 (HIGH, NEW in v0.1.12) — Recast crashes at `cast-flow.js:99` with "undefined id"

**Severity:** HIGH (blocks R38 Trigger D)
**Status:** OPEN — no fix attempted (per user constraint)

**Repro:**
1. Cast Manifest Tulpa (first Tulpa) — must succeed somehow despite REG-1 (in this session, the first cast happened during a session where REG-1 was intermittent)
2. Without dismissing first Tulpa, cast Manifest Tulpa again
3. Observe console

**Expected:** First Tulpa dismissed (anchor + token + system AE swept — Bug 1 fix behavior); cast dialog opens for second Tulpa; second Tulpa placed.

**Actual:**
- First Tulpa dismissed correctly — anchor AE deleted, token removed, system AE swept (Bug 1 working as designed)
- Second Tulpa placement attempt produces console error: `Error: undefined id [GRhO38Y2RLiYL8lj]` originating at [cast-flow.js:99](../../../modules/cast-flow.js#L99) (`await postCast({ caster, tulpa, castConfig });`)
- No second Tulpa is placed

**Root cause hypothesis:**
- `postCast` is awaiting an operation that references a document ID that no longer resolves. Two candidates:
  - (a) The previous anchor AE's delete cascade is racing with the new cast — `postCast` may attempt to write to the just-deleted previous anchor's AE collection before the cascade has settled
  - (b) The new Tulpa token captured at [cast-flow.js:45](../../../modules/cast-flow.js#L45) is captured before the dialog opens; if the previous-anchor delete cascade invalidates downstream state (e.g. flushes the recently-summoned token's flag mid-flight), `postCast` may consume a stale `tulpa.id`

**Suggested fix (NOT applied):**
1. Log `tulpa.id`, `tulpa?.actor?.id`, `caster.id`, and `castConfig` immediately before `await postCast(...)` at line 99
2. Reproduce the recast crash with logging enabled to identify which ID is undefined
3. Likely fix: explicitly await the previous-anchor delete cascade (e.g. `await previousAnchor?.delete()` returning before the new cast proceeds) rather than relying on `deleteActiveEffect` hook fan-out timing. The previous-anchor deletion happens at [cast-flow.js:34-37](../../../modules/cast-flow.js#L34-L37) — that delete is awaited, but the downstream cascade (`onDeleteActiveEffect` → token delete → system AE sweep) is fire-and-forget. The new cast may proceed before the cascade settles.
