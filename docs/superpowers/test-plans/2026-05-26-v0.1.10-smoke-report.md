## Executive Summary

v0.1.10 fixes the BLOCKING deepClone/Set bug from v0.1.9 that prevented the base damage type from being applied to the Manifestation Strike. The fix (`toTypesArray()` and `freshenPart()` in modification-registry.js) correctly normalizes Set/Array/Object types before writing the strike update. This was confirmed working across radiant and psychic damage types.

However, v0.1.10 carries forward two medium-severity bugs from v0.1.9 (wrong dismiss reason text, orphaned system summon AE), introduces one new HIGH-severity bug (Harrowing Presence aura does not propagate markers to in-range tokens), and exposes one LOW-severity data accuracy bug (aura distance formula is 10ft instead of the spell text's 15ft).

Testing was partially blocked by a page reload loop affecting the test world, though the scope of this blockage was overstated in the original report. Post-test review revealed that at least one cast attributed to "page reload failure" actually completed the full cast flow and entered the dnd5e summoning placement crosshair; the tester failed to recognize the crosshair state and did not click to place the token. The page reload loop is real (init cycle timestamps are in the console log), but the number of genuinely blocked casts is uncertain. Bug 6 has been downgraded from HIGH to MEDIUM and partially retracted.

### R25: deepClone/Set Fix -- PASS (FIXED from v0.1.9)

**This was the v0.1.9 BLOCKING bug.** In v0.1.9, `foundry.utils.deepClone` converted `DamageData.types` (a `Set` in dnd5e 5.2.5) into a plain object `{0: "bludgeoning"}`, which `item.update()` silently rejected. Confirmed working: Cast 1 (radiant) correctly set Part 0 types to `["radiant"]` on the synthetic actor. Cast 2 (psychic) correctly set types to `["psychic"]`.

## Bugs Found

### Bug 1 (MEDIUM): Wrong dismiss reason on anchor AE deletion -- CARRIED FORWARD from v0.1.9

**Severity:** Medium (misleading but cosmetic)
**Status:** Still present in v0.1.10 (same as v0.1.9 Bug 3)
**Reproduction:** Delete the "Manifest Tulpa (active)" anchor AE from the caster via any means. Observe the dismiss chat card text.
**Expected:** "Tulpa fades -- the anchor effect was removed" or similar.
**Actual:** "Tulpa fades -- the token was removed manually."

**Root cause:** `inferReason()` in dismiss-flow.js (line 107) has a five-step reason ladder:
1. `options[MODULE_ID].dismissReason` (set by recast/zeroHP/manual paths)
2. `effect.getFlag(MODULE_ID, "dismissReason")` (legacy path)
3. Caster has `dead` status
4. Caster HP <= 0
5. Anchor duration expired

When none match, it defaults to `"manual"`. The issue is twofold:
- When the anchor AE is right-click deleted from the effects panel, no options are passed, so step 1 misses.
- The `"manual"` reason's template text says "the token was removed manually," which is misleading because the *anchor AE* was removed, not the token. The token gets deleted by the *cascade*, not by the user.
- Additionally, the dismiss code calls `tokenDoc.delete()` which triggers `onPreDeleteToken`, which finds and deletes the anchor AE again with `dismissReason: "manual"`. By this point the anchor is already being deleted, but the reason gets overwritten to "manual" in the re-entrant call.

**Suggested fix:** Add a new reason category `"anchorRemoved"` for the case where the anchor AE is manually deleted without an explicit reason. The fallback in `inferReason` should check whether the anchor was the entity being deleted (which it always is in this flow) and use the appropriate label. The template text for `"manual"` should say "the anchor effect was removed" rather than "the token was removed manually."

### Bug 2 (MEDIUM): Orphaned system "Summon: Manifest Tulpa" AE -- CARRIED FORWARD from v0.1.9

**Severity:** Medium
**Status:** Still present in v0.1.10 (same as v0.1.9 new bug)
**Reproduction:** Cast Manifest Tulpa, then dismiss via any trigger. Check the caster's effects list.
**Expected:** Both the module's "Manifest Tulpa (active)" anchor AE and the dnd5e system's "Summon: Manifest Tulpa" AE are removed.
**Actual:** The module's anchor AE is removed but the system's "Summon: Manifest Tulpa" AE remains on the caster.

**Root cause:** The dismiss flow in dismiss-flow.js only looks for and processes the module's anchor AE (identified by the `flags.manifest-tulpa.tulpaUuid` flag). It has no logic to also remove the dnd5e system-generated "Summon: Manifest Tulpa" AE, which is created by the native summoning activity.

**Suggested fix:** At the end of `onDeleteActiveEffect`, after the dismiss chat card is posted, find and delete the system summon AE:
```javascript
const summonAE = caster.effects.find(e =>
  e.name.startsWith("Summon:") && e.name.includes("Manifest Tulpa")
);
if (summonAE) await summonAE.delete();
```
This should use a more robust identifier if available (e.g., checking `flags.dnd5e.summon` for the matching origin UUID).

### Bug 3 (HIGH): Harrowing Presence aura does not propagate markers -- NEW in v0.1.10

**Severity:** High (the feature is entirely non-functional)
**Status:** New finding (not tested in v0.1.9)
**Reproduction:**
1. Cast Manifest Tulpa with Harrowing Presence modification selected
2. Place an NPC token within 5ft of the Tulpa (well within the 10ft aura radius)
3. Start combat, advance turns, move tokens in and out of range
4. Check the NPC's effects and flags

**Expected:** The NPC receives a marker effect from Aura Effects containing `flags.manifest-tulpa.inHarrowingAura = true` and `flags.manifest-tulpa.auraDC = 15`.
**Actual:** The NPC receives no effects at all. The aura visual (purple rectangle) renders correctly on the canvas, and the aura AE on the Tulpa has the correct data, but the marker never propagates.

**Diagnostic data confirmed correct:**
- Aura AE type: `"auraeffects.aura"` -- correct
- `system.distanceFormula`: `"10"` -- valid (see Bug 4 for accuracy)
- `system.disposition`: `-1` (hostile) -- correct for the Tulpa (friendly) targeting hostile NPCs
- `system.collisionTypes`: `Set(["move"])` -- correct (verified via `toObject()` serialization)
- `system.combatOnly`: `false` -- correct
- `system.script`: `"true"` -- correct (always-apply)
- `changes` array: Two entries for `inHarrowingAura` and `auraDC` -- correct in `toObject()` output, suppressed in live object (expected Aura Effects behavior)
- Tulpa disposition: 1 (friendly), NPC disposition: -1 (hostile) -- correct relationship for the aura's `-1` disposition target

**Testing performed (all with no propagation):**
- NPC placed at 5ft from Tulpa (well within 10ft range)
- **Combat started** with all three tokens (PC, Tulpa, NPC) as combatants, combat round 1 turn 0
- Combat advanced through multiple turns (round 1, turns 0-2)
- NPC moved in and out of range **during active combat** via `document.update()` with 1-second waits
- Tulpa (aura source) moved during combat to trigger source-side recalculation
- Aura Effects `migrateActiveAuras()` API called explicitly
- Combat ended, NPC moved outside and back inside range without combat
- **None of these triggered marker propagation.** The NPC's effects array and `flags.manifest-tulpa` remained empty throughout.

**Root cause analysis:** The aura data is structurally correct and matches the full Aura Effects 1.5.2 schema (including the critical `collisionTypes: ["move"]` that was missing in v0.1.7). The aura visual rendering confirms Aura Effects recognizes the effect as an aura. The failure is in the propagation step, not the creation step.

Possible causes:
- **Unlinked token actors:** The Tulpa uses an unlinked token. Aura Effects may not support auras on unlinked/synthetic actors. The aura AE is stored on the token delta, not a world actor, and Aura Effects may only scan world actors for aura sources.
- **Programmatic creation:** The aura AE is created via `createEmbeddedDocuments("ActiveEffect", [...])`. Aura Effects may require a different creation pathway (e.g., drag-drop from the effects panel) to register the aura for proximity scanning.
- **Module timing:** The aura AE is created as part of the cast-flow's `applyModifications` batch. Aura Effects may need a specific hook or initialization event to become aware of new aura sources that doesn't fire during programmatic creation.

**Suggested investigation:** Create the same aura AE manually on a world actor (not a summoned token) using the Aura Effects effects panel UI. If it propagates there, the issue is unlinked-token-specific. If it doesn't, the issue is in the aura schema or a broader Aura Effects compatibility problem. Also check the Aura Effects 1.5.2 source code for how it discovers aura sources (does it scan `canvas.tokens` or `game.actors`?).

**Severity:** Low (data accuracy, not functionality)

**What:** `distanceFormula` is hardcoded as `"10"` (10-foot radius).
**Expected:** The spell text describes a "15-foot aura" for Harrowing Presence.
**Actual:** The aura radius is set to 10 feet.

**Suggested fix:** Change `distanceFormula: "10"` to `distanceFormula: "15"` in the `harrowingPresence.build()` function.

### Bug 5 (LOW): Cast dialog has no scrollbar -- NEW in v0.1.10

**Severity:** Low (usability issue)
**Status:** New finding
**Location:** cast-dialog.js line 40 (`position: { width: 480, height: "auto" }`), manifest-tulpa.css (no `overflow` or `max-height` rule)

**What:** The cast dialog uses `height: "auto"` in its ApplicationV2 position config and has no `overflow-y` or `max-height` in its CSS. The dialog content includes damage type radio buttons, 6 modification categories (Morphic with 8 entries including 5 size shifts, Combat with 4 entries, Resistance with 10 entries, Movement with 4 entries, Skill with 18 entries, Special with 1 entry), plus a slot counter and submit/cancel buttons. On standard viewports this extends well past the visible screen area.

**Impact:** Users must mouse-wheel scroll within the dialog to reach lower modification categories and the submit button. There is no visual scroll indicator, so a user unfamiliar with the dialog structure may not realize there are more options below the fold. The dialog also cannot be resized vertically.

**Suggested fix:** Add a `max-height` and `overflow-y: auto` to `.mt-cast-body` or the dialog's content area:
```css
.manifest-tulpa-dialog .mt-cast-body {
  max-height: 60vh;
  overflow-y: auto;
}
```
Alternatively, set `position: { height: 600 }` (or similar fixed height) in the ApplicationV2 options to make the dialog a fixed-height scrollable window. The footer with submit/cancel buttons could be pinned outside the scroll area using `position: sticky; bottom: 0;`.

## Appendix: Code Changes Verified

### modification-registry.js

New functions added in v0.1.10:

**`toTypesArray(t)`** (line 27): Coerces a damage-part `types` field of any shape into a plain JS array. Handles `Set`, `Array`, plain `{0: "bludgeoning"}` objects (from `deepClone` degradation), and `undefined`. This is the core fix for the v0.1.9 BLOCKING bug.

**`freshenPart(p)`** (line 38): Spreads a damage part into a plain object using `toObject()` when the part is a DataModel instance (preserving non-enumerable getter fields), then replaces `types` with a plain array via `toTypesArray`. Falls back to a shallow spread for plain-object test fixtures.

**`buildStrikeParts(parts, damageType, itemPatches)`** (line 56): Pure function that builds the final `damage.parts` array for one activity. Reads parts, normalizes each via `freshenPart`, sets Part 0's types to `[damageType]`, then runs every item-patch modification's `patchActivity` transformer.
