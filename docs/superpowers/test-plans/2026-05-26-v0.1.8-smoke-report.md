#### R8: Damage Type Set by Cast Dialog -- FAIL (BLOCKING)

**Selected:** "Psychic" damage type in cast dialog (second cast).
**Expected:** Manifestation Strike damage types change from bludgeoning to psychic on both activities' Part 0.
**Actual:** Both activities' Part 0 still shows `types: ["bludgeoning"]`. Part 1 (Empowered Strikes) correctly shows `types: ["psychic"]`.

**Root cause analysis:** The `setStrikeDamageType` function at `cast-flow.js` lines 118-133 uses `iterActivities` (confirmed working) and writes `parts[0].types = [damageType]`. The update key is `system.activities.${actId}.damage.parts`. Two hypotheses for why the change doesn't persist:

1. **Set vs. Array serialization**: In dnd5e 5.2.5, `damage.parts[].types` may be stored internally as a `Set`. The `deepClone` at line 127 produces a plain array copy, but when the update merges back, Foundry's data model may normalize `[damageType]` back through the schema's Set constructor, and the merge path may not detect a change from `Set(["bludgeoning"])` to `Array(["psychic"])` as dirty.

2. **Update ordering**: `setStrikeDamageType` runs at line 68, then `applyModifications` runs at line 71. The `empoweredStrikes.patch` also writes to `system.activities.${actId}.damage.parts` (it appends a new part). If Foundry batches these updates, the second write (which includes a `deepClone` of the original parts array before `setStrikeDamageType`'s change has been applied to the in-memory document) may overwrite the first. This is the more likely cause: the Empowered Strikes patch clones `act.damage?.parts` *from the in-memory document*, which may not yet reflect the `strike.update()` from `setStrikeDamageType` because Foundry's embedded document update pipeline is asynchronous.

**Recommended fix:** Merge the base-type assignment into the `empoweredStrikes.patch` itself (or into a single combined update call) rather than relying on two separate `strike.update()` calls whose effects may race. Alternatively, ensure `setStrikeDamageType`'s `await strike.update()` fully resolves and the in-memory document reflects the change before `applyModifications` reads from it.

This is the same symptom as v0.1.7 Bug A (R8) but with a different root cause. The iteration fix is correct; the persistence/ordering issue is new.

#### R17: Relentless Clamp + Post-Relentless zeroHP Path -- PARTIAL PASS

**First lethal hit (Relentless clamp):** Tested. Tulpa HP was set to 0 via direct update. The `preUpdateActor` hook fired, detected Relentless was available and unused, and mutated `changes` to clamp HP to 1. Chat card "Relentless triggers" posted. `relentlessUsed` flag was set.

**Second lethal hit (post-Relentless zeroHP):** NOT CONCLUSIVELY TESTED. Between the first and second damage attempts, the page appeared to reload (console showed fresh `manifest-tulpa | init` and `manifest-tulpa | ready` messages), which reset the Tulpa's state to 90/90 HP and cleared the `relentlessUsed` flag. The `restoreTulpaHpWatchers` function at `tulpa-hp-watcher.js` lines 63-72 re-arms watchers at world load, but the `relentlessUsed` flag was stored on the Tulpa actor via `setFlag` -- a page reload should preserve it since it's persisted to the database. The flag loss suggests the `await actor.setFlag()` inside the `preUpdateActor` hook (an async call in a synchronous hook) may not have completed before the page reloaded.

**Latent concern:** The `preUpdateActor` hook handler is declared `async` (`tulpa-hp-watcher.js` line 15), but Foundry V13's hook system does not await async handlers -- it calls them and discards the returned Promise. This means `await actor.setFlag(MODULE_ID, "relentlessUsed", true)` at line 22 and `await anchor.setFlag(MODULE_ID, "dismissReason", "zeroHP")` at line 35 are fire-and-forget from Foundry's perspective. If the actor update that triggered the hook completes and a subsequent operation (page reload, another update) runs before the `setFlag` write resolves, the flag is lost. The `foundry.utils.setProperty(changes, "system.attributes.hp.value", 1)` at line 22 is synchronous and correctly mutates the pending update, but the flag writes are not protected by the same synchronous mutation path.

**Recommendation:** Move the `relentlessUsed` flag write into the synchronous `changes` mutation (e.g., `foundry.utils.setProperty(changes, "flags.manifest-tulpa.relentlessUsed", true)`) so it piggybacks on the same `updateActor` call the hook is intercepting. This eliminates the race entirely.

## Bugs Found

### Bug A: setStrikeDamageType Part 0 Update Not Persisting (BLOCKING)

**Severity:** Critical (base damage type never changes from bludgeoning)
**Affects:** R8, R20
**Files:** `cast-flow.js` lines 118-133 (setStrikeDamageType), lines 68 + 71 (call ordering)

**Symptom:** After casting with a non-bludgeoning damage type, Part 0 of each Manifestation Strike activity retains `types: ["bludgeoning"]`. Part 1 (added by Empowered Strikes) correctly shows the chosen type, proving `iterActivities` works.

**Root cause hypothesis (high confidence):** `setStrikeDamageType` at line 68 calls `await strike.update(...)` to set Part 0's types. Then `applyModifications` at line 71 runs `empoweredStrikes.patch`, which calls `deepClone(act.damage?.parts)` to read the current parts array. If the in-memory document has not yet reflected the first update (Foundry's embedded document update pipeline may buffer writes), the `deepClone` captures the stale pre-update state. The `empoweredStrikes.patch` then calls `strike.update(...)` with a parts array that has the correct Part 1 appended but Part 0's types still set to `["bludgeoning"]`, overwriting `setStrikeDamageType`'s change.

**Evidence:** Part 1 appears with the correct damage type (Empowered Strikes patch runs second and appends successfully). Part 0 reverts to bludgeoning (Empowered Strikes patch's stale clone overwrites the first update).

**Proposed fix:** Merge the base damage type assignment into the `empoweredStrikes.patch` function, or restructure so both writes happen in a single `strike.update()` call. For the case where Empowered Strikes is not selected, `setStrikeDamageType` alone should work correctly since no second write would overwrite it. Test both: (a) damage type only (no Empowered Strikes), and (b) damage type + Empowered Strikes.

### Bug B: Async Handlers in preUpdateActor Hook (LATENT)

**Severity:** Medium (race condition, not always triggered)
**Affects:** R17 (Relentless flag persistence)
**File:** `tulpa-hp-watcher.js` lines 15-42

**Symptom:** `relentlessUsed` flag may be lost if a page reload or subsequent update occurs before the `await actor.setFlag()` resolves. Observed during testing when the page reloaded between Relentless clamp and the second lethal hit, with the Tulpa returning to 90/90 HP and no `relentlessUsed` flag present.

**Root cause:** Foundry V13's hook system calls `preUpdateActor` handlers synchronously. If the handler is declared `async`, Foundry calls it, receives a Promise, and discards it. The synchronous mutation (`foundry.utils.setProperty(changes, "system.attributes.hp.value", 1)`) works because it modifies the pending update object before Foundry processes it. But `await actor.setFlag()` at line 22 initiates a separate database write that Foundry doesn't know about or wait for.

**Proposed fix:** Replace the separate `setFlag` call with a synchronous mutation that piggybacks on the same update:

```js
foundry.utils.setProperty(changes, "flags.manifest-tulpa.relentlessUsed", true);
```

This embeds the flag in the same `updateActor` call Foundry is already processing, eliminating the race. The `await postRelentless()` and `await playRelentless()` calls (chat card + animation) can remain async since they don't affect game state that other hooks depend on.

Similarly, the zeroHP path's `await anchor.setFlag(MODULE_ID, "dismissReason", "zeroHP")` at line 35 followed by `await anchor.delete()` at line 36 has the same issue: the `setFlag` may not resolve before the hook returns. Consider combining these into a single `anchor.update({ flags: { ... } })` followed by `anchor.delete()`, or accept that the dismiss reason may occasionally fall through to the "duration" default.

### Bug C: Minor -- Anchor AE Dismissal Text for Manual Delete

**Severity:** Low (cosmetic)
**Affects:** Dismiss flow text accuracy

**Symptom:** When the anchor AE is deleted manually (not via one of the five named triggers), the `inferReason` function at `dismiss-flow.js` lines 83-88 falls through to `"duration"` as the default reason. This produces "Tulpa Dismissed: duration" even when the actual cause was manual intervention.

The function only returns a tagged reason if `dismissReason` was explicitly set on the anchor before deletion. The recast path (line 33) and zeroHP path (`tulpa-hp-watcher.js` line 35) tag correctly, but direct manual AE deletion by the GM does not go through any tagging path.

**Proposed fix:** Change the default fallback from `"duration"` to `"removed"` or `"unknown"`, or detect manual AE deletion via the `options` parameter in the `deleteActiveEffect` hook.
